Plan · 13 Nov 2026 · Swift Circuits, Greenside Partee, SkiCut, Tally, Ad Sentinel

Move all payments into one g3-payments crate

Every app that takes money gets it through one crate. g3-entitlements folds into it, the Stripe and Apple code that exists twice today becomes one copy, and SkiCut, Tally and Ad Sentinel get trials and paid unlocks from the same code.

Two facts that shape the plan

Ad Sentinel is a phone app, so in Google Play and the App Store it must sell through store billing, not Stripe license keys. And SkiCut, Tally and Ad Sentinel have no server, so the crate must also run as a small standalone server for apps that have none.

The crate

One repository, g3techhq/g3-payments, same conventions as g3-cache (AGENTS.md, CHANGELOG, deny.toml, justfile, lefthook, CI workflows). Unpublished git dependency until Dioxus 0.8, like the other g3 crates, and added to Projects/.cargo/config.toml for local builds.

Decisions

QuestionRecommendationWhy
Stripe clientchanged Stripe's REST API over reqwest, pinned to 2026-08-26.dahliaOne HTTP stack for every provider and no release-candidate pin. Greenside's gateway behaviour (idempotency, retries, replayed-session fallback) is kept.
Cryptoadded ring for TLS, token signing and webhook HMACsNo aws-lc enters through the crate, so no NASM on Windows and no two-backend panic.
Apple verificationGreenside's chain check for every JWS, plus SC's Server API callStrongest of the two, and Swift Circuits gains refund notifications its docs list as pending.
jsonwebtokenVersion 10 with aws_lc_rs everywhereSC's comment: SurrealDB turns on aws_lc_rs, and mixing backends panics. Greenside moves off 9.3.1.
Where records livechanged A Store trait. Swift Circuits and Greenside each implement it over their own tables. The crate's SurrealDB store serves new apps and the standalone server, and is built in step 6.No data migration for live Greenside subscriptions. Moving them to an entitlement table can come later, on its own.
Account-bound endpointsStay as thin server fns in each app that call PaymentsServiceThey need the app's session and User. Webhook and license routes need neither, so the crate ships those as an axum router.
Apps with no serverOne g3-payments-server binary on the same machine, configured with several appsSkiCut and Tally need a Stripe webhook and license activation somewhere. One binary serves both, and any later serverless app.
Where Tally keeps its licenseIn per-machine app data, never inside the books fileThe books file is shared between computers. A license inside it would carry one machine's activation to every computer that opens the books.
What happens when Tally's trial endsThe books go read-only: open, view, run reports, export. Only editing and downloads need the license.It's someone's financial records. Locking a person out of their own books would be the wrong default, and they'd lose trust in the app.
Ad Sentinel purchasesChecked on the phone: StoreKit JWS via apple_jws, Play via the purchase signatureNo server to run. A trial clock from license gives the 14 days; the unlock is a store purchase.
Microsoft StoreLeave out for now; Provider gets room for itSkiCut sells directly first.

Rules that keep live apps working

  • Same webhook URLs. /api/v1/stripe_webhooks and /api/v1/app_store_notifications stay where they are, so nothing changes in the Stripe dashboard or App Store Connect.
  • Same wire format. EntitlementSnapshot serializes byte-for-byte as today. Phones already store it (swift-circuits-device-purchases-v1) and cache it. A fixture test pins the JSON.
  • Old clients survive new fields. Provider gains LicenseKey and a #[serde(other)] Unknown catch-all; expires_at_unix is optional and skipped when empty.
  • One Stripe account, many apps. Every checkout carries metadata.g3_app; each endpoint ignores other apps' events and still answers 200.
  • Schema changes are additive. Swift Circuits ships a reviewed SurrealKit rollout plan (its AGENTS.md rule); the old image can still run against the new schema, so rollback is a redeploy.
  • Server deps stay optional. CI builds with no features and for wasm32 so Stripe or SurrealDB never leak into a client build.

Steps, in order

All work commits straight to main in each repo. Steps 4 and 5 can run side by side once step 3 lands; 6 and 7 can run side by side once step 2 lands.

  1. Create the repo

    • g3techhq/g3-payments with g3-cache's scaffolding, version 0.1.0, the feature list above.
    • Local patch entry in Projects/.cargo/config.toml; git patch entry in each app manifest.
    • CI: no-features build, wasm32 build, iOS/Android target lint, each feature alone, all features.

  2. Move the shared core

    • entitlements from g3-entitlements with its tests, plus the forward-compatible Provider and expires_at_unix.
    • catalog type; apple_jws from Greenside with its testdata fixtures and Apple Root CA G3 cert.
    • JSON fixture test for today's snapshot format.

  3. Move the server side done

    • server::stripe from Greenside's gateway and webhook, with a one-time Checkout mode built from SC's flow (paid-session check, async success and failure, refunds).
    • server::app_store merging SC verification with Greenside's subscription state and notifications; server::play from SC.
    • Store trait, server::claims and custody from SC, SurrealDB implementation and its .surql schema files.
    • axum router for webhooks and license routes; every test from both apps comes along.

  4. Switch Swift Circuits

    • Delete crates/g3-entitlements; imports become g3_payments::.
    • payments.rs, native_purchase.rs, purchase_custody.rs, native_pending.rs and store.rs shrink to catalog data, thin server fns and UI.
    • Mount the router; wire App Store Notifications V2 (new for this app).
    • SurrealKit rollout plan for any table changes; update docs/accounts-payments.md and docs/architecture.md.

  5. Switch Greenside Partee

    • billing/ keeps membership.rs, server.rs and the app half of server_impl.rs; the rest is deleted.
    • Implement Store over the existing User subscription fields. No data migration.
    • jsonwebtoken 9.3.1 → 10 with aws_lc_rs.

  6. Build the new pieces

    • license: trial clock with clock-rollback guard, Ed25519 license file check, activation client, fail-open 30-day re-check.
    • server::surreal: the Store on SurrealDB, designed together with the license tables (moved here from step 3).
    • server::license_keys: key issue on paid checkout, machine-limited activation, signing key from an env secret, revoke on refund.
    • native: on-device Play signature check beside the StoreKit check.
    • g3-payments-server binary: multi-app config file, Docker image like the other servers.

  7. Add SkiCut, Tally and Ad Sentinel

    • SkiCut: license feature, trial banner, license entry screen, Stripe product, deploy the standalone server behind your proxy.
    • Tally: the same license setup and a second Stripe product on that server. License stored in app data, not the books file. Read-only mode after the trial.
    • Ad Sentinel: native + trial clock, Play product (iOS later), paywall after day 14. Sideloaded builds can take a Stripe license instead.

  8. Test in every sandbox, then deploy

    • Stripe test mode through stripe listen: buy, async payment, refund, subscription renew, cancel, portal.
    • StoreKit sandbox and Play license testers: buy, restore, refund, signed-out purchase.
    • Deploy order: Swift Circuits and Greenside (each schema rollout first), then the standalone server, then the two new app builds.
    • Watch Stripe's webhook delivery page and App Store notification history for a day after each deploy.

Risks

high Greenside renewals

Live subscriptions renew through the webhook. A routing bug means a paying member is shown as lapsed. Mitigation: the Store trait keeps its data where it is, and its existing webhook tests must pass unchanged before deploy.

high Swift Circuits device records

Phones hold serialized snapshots. A format change re-locks paid content. Mitigation: the JSON fixture test and the Unknown catch-all.

medium Stripe rewrite in SC

SC moves from raw reqwest to async-stripe. Mitigation: replay SC's webhook test payloads through the new handler.

medium Doing it all at once

Two live apps change in the same window. Mitigation: deploy them a day apart even though the code lands together; every schema change is additive so rollback is a redeploy.

Open questions for you

  • Domain for the standalone server, for example pay. on your main domain.
  • Ad Sentinel price and trial in Play: a $10 one-time unlock after a 14-day clock, or the same free-then-unlock model as Swift Circuits.
  • Machine limit per SkiCut and Tally license (3 is common). Tally's books are shared between computers, so a household may need more than one.
  • Whether Greenside's subscription records should move to the shared entitlement table later, or stay on User for good.
